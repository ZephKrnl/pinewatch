# M2c: Assets Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Find, read and index the game's asset definitions exactly as the game's `Assets` and `AssetsWorker` do:
the search locations and their order, the folder walk and file precedence, `MasterBundle.dat`, the per-file hashes,
translations with English fallback, the asset header (GUID, type, legacy ID, master bundle, bundle path), the GUID and
legacy-ID index with `AddToMapping`'s rules and messages, the asset references of `UnturnedDatEx`, and the first
asset type with its data, `LandscapeMaterialAsset`, with its holiday redirects (V14).

**Architecture:** A new `pinewatch-assets` crate on top of `pinewatch-dat`, `pinewatch-io` and `pinewatch-mono`.
`System.IO.Path`'s string functions move to `pinewatch-io`, so the level and asset messages build paths the same
way. The worker's threads become an explicit, deterministic sequence (L5): each search location is searched and read
in the original's order, and locations are taken in the order they were requested. Nothing writes to the install
(L3).

**Tech Stack:** Rust 1.99.1, edition 2024. Production dependencies: `sha1` (already allowed). No new crates.

**Spec:** `docs/superpowers/specs/2026-11-01-file-format-readers-design.md` (sections 3, 4, 6), `COMPATIBILITY.md`,
`docs/VERIFICATION.md`.

## Where this plan sits

| Plan | Delivers |
|---|---|
| M2a `.dat` reader | Done |
| M2b Reference harness | Waits for the Windows PC (Unity, the game, its Mono runtime) |
| **M2c Assets** (this plan) | `pinewatch-assets` as described above |
| M2d Asset processor | Textures for landscape materials, through Unity on the Windows PC |
| M2e Terrain materials | The landscape's original materials |

M2c comes before M2b here because M2b needs the Windows PC and M2c doesn't. M2b's harness will then check M2c too.
This plan was written and started on 2026-11-02 in a cloud session, under the owner's order to continue
autonomously; it is reviewed together with the work on the branch before `main` moves.

## Global Constraints

- Target U3-SDK `v3.26.3.12` (commit `aba323a`). C# paths are relative to
  `reference/u3-sdk/Assets/Runtime/Assembly-CSharp/Unturned/`.
- Parity rules P1 to P8 from the spec apply to every line. Messages are exact and in order (P4); exceptions are values
  (P3); the parser each search location reuses is shared state (P2).
- **Build configuration.** The port follows the shipped Windows client: `UNITY_STANDALONE_WIN` and `WITH_NOREDIST`
  defined; `UNITY_EDITOR`, `DEVELOPMENT_BUILD` and `DEDICATED_SERVER` not defined. The SDK project itself doesn't
  define `WITH_NOREDIST`, so this is an assumption (new VERIFICATION entry V21, checked against the shipped
  `Assembly-CSharp.dll`). Command-line flags keep their defaults: `-ParseAssetMetadata`, `-ResaveAssets`,
  `-ValidateAssets` and `-LogWorkshopAssets` are off.
- **Out of scope here:** workshop and server search locations (no Steam UGC service yet, dedicated server is M7),
  loading Unity asset bundles (M2d), `PopulateAsset` for asset types other than `LandscapeMaterialAsset`, spawn
  linking, reloading and the server asset mapping.
- **Never write to the install (L3).** Where the original writes (a GUID added to a definition without one, a missing
  `Sandbox` folder created), the register says what Pinewatch does instead.
- **Thread order (L5).** The original runs a searcher and a reader thread per search location, all at once. Pinewatch
  produces one order the original can produce: locations in request order; inside a location, the reader's order,
  with each searcher exception placed where the searcher raised it.
- No game content in the repository. Tests build synthetic install trees; install tests only read.
- Every ported behavior that neither the shipped IL nor a ported test confirms gets a `docs/VERIFICATION.md` entry.
- Work on the session branch; commits authored by Zeph; no AI attribution.

## Review Focus

1. **Order.** Folder walk (breadth-first), file precedence (`<Folder>.asset`, `<Folder>.dat`, `Asset.dat`, then every
   `*.asset`), and the place of each exception message (Tasks 3 and 4).
2. **Hashes.** A definition's hash is the SHA-1 of the bytes its reader pulled; a master bundle asset's hash also
   covers its lower-case bundle path (Tasks 4 and 6).
3. **Index messages.** `legacy ID … already taken by …`, `GUID already taken by …` and `needs a non-zero ID`, with the
   other asset's friendly name and origin (Task 9).
4. **Paths in messages.** Absolute, built like `Path.Combine` on the platform, so they match the game's log on Windows.

### Task 2: Origins and search locations

**Files:** `crates/pinewatch-assets/src/{origin.rs,search.rs}`, `crates/pinewatch-assets/tests/search.rs`

Sources: `Bundles/Assets.cs` (`LoadAllAssets`, `AddSearchLocation`, `AddSandboxSearchLocations`,
`AddMapSearchLocations`, `FindOrAddLevelOrigin`), `Bundles/AssetOrigin.cs`, `Level/Level.cs` (`ScanKnownLevels`,
`ReadLevelInfo`), `Files/ReadWrite.cs`.

- `AssetOrigin { name, workshop_file_id, should_assets_override_existing_ids, can_resave }`, with the four built-in
  origins in `LoadAllAssets`' order: `Vanilla Built-in Assets`, `Reloaded Assets (Debug)` (overrides IDs),
  `Server Common (Legacy)`, `Per-Server (Legacy)`.
- The client's locations, in order: `<root>\Bundles`; client UGC (none without the workshop service); each folder of
  `<root>\Sandbox` in enumeration order, logging `Sandbox: <name>` and getting an origin
  `Sandbox Folder "<name>"` that overrides IDs and can resave; each map's `Bundles` folder, maps in
  `Directory.GetDirectories(<root>\Maps)` order, for maps `ReadLevelInfo` accepts (`Level.dat` exists and reads).
- `AddSearchLocation` logs `<origin name> added asset search location "<full path>"`.
- A missing `Sandbox` folder: the original creates it; Pinewatch doesn't (L3 (d)).
- Level discovery's own messages (`Discovered level …`, `Config.json` errors, version errors) come with level info,
  which needs the JSON reader: a gap entry in `VERIFICATION.md`.

### Task 3: The folder walk

**Files:** `crates/pinewatch-assets/src/worker.rs`, `crates/pinewatch-assets/tests/walk.rs`

Source: `Bundles/AssetsWorker.cs` (`SearcherThreadMain`, `FindAssets`).

- Breadth-first: a queue starting with the location; for each folder, `MasterBundle.dat` (by `File.Exists`), then
  `FindAssets`, then its subfolders (`Directory.EnumerateDirectories` order) appended to the queue.
- `FindAssets`: `<Folder>.asset`, else `<Folder>.dat`, else `Asset.dat`, else every `*.asset` (in
  `Directory.EnumerateFiles(dir, "*.asset")` order).
- Each exception becomes the exact message (`Caught exception checking for assets at: "<path>"`, `… in: "<dir>"`,
  `Caught exception finding asset subdirectories in: "<dir>"`, `Caught exception reading master bundle config at:
  "<path>"`) with the exception.
- New VERIFICATION entry: how Mono's `EnumerateFiles` matches `*.asset` on Windows (case, short names, the 3-letter
  extension rule) and whether its order equals `FindNextFile`'s.

### Task 4: Reading definitions and translations

**Files:** `crates/pinewatch-assets/src/worker.rs`, `crates/pinewatch-assets/tests/read.rs`

Source: `Bundles/AssetsWorker.cs` (`ReaderThreadMain`, `AddFoundAsset`, `ReadFileWithoutHash`).

- One `DatParser` per location, reused for every definition, translation and `MasterBundle.dat` there, with metadata
  off (P2).
- A definition's result: its path, tree, a copy of the parser errors (or none), the SHA-1 of the file, and the
  translation trees: `<Language>.dat` if it exists (plus `English.dat` as fallback when the language isn't English),
  else `English.dat`, else none.
- A failure becomes `Caught exception reading asset definition at: "<path>"` with the exception (V12 for I/O texts).
- Exceptions are logged as `UnturnedLog.exception(e, message)` does: the message, then the exception's message
  (`(empty exception message)` if empty); the stack-trace line is L1.

### Task 5: Master bundles

**Files:** `crates/pinewatch-assets/src/master_bundle.rs`, `crates/pinewatch-assets/tests/master_bundle.rs`

Sources: `Bundles/MasterBundleConfig.cs`, `Bundles/MasterBundleHelper.cs`, `Bundles/Assets.cs`
(`findMasterBundleByPath`, `findMasterBundleByName`, the master bundle branch of `LoadAssetsFromWorkerThread`).

- `MasterBundleConfig::new(directory, data, origin)` with its exact exceptions (`System.Exception`, new
  `ExceptionKind::Exception`): missing `Asset_Bundle_Name`, missing `Asset_Prefix`, version out of range, bundle file
  missing (`… Expected path: <path>`); `Master_Bundle_Version` before `Asset_Bundle_Version` (default 2).
- `asset_bundle_path` (Windows, `WITH_NOREDIST`: `Path.Combine(directory, name)`), `hash_file_path`,
  `does_hash_file_exist`, `format_asset_path`.
- The bundle file's SHA-1 over its whole content; the bundle bytes themselves are not kept (M2d loads bundles).
- Loading always succeeds here, as it does for the game's own bundles. Unity refusing a second bundle with the same
  content (the "fallback asset bundle" messages) needs the bundle reader: a gap entry.

### Task 6: Asset headers

**Files:** `crates/pinewatch-assets/src/load.rs`, `crates/pinewatch-assets/tests/load.rs`

Source: `Bundles/Assets.cs` (`TryLoadFile`, `LoadFile` up to `Activator.CreateInstance`, `reportError`,
`getExceptionMessage`).

- The messages, in order: path longer than 260 characters; each parser error (`Error parsing "<path>": "<error>"`);
  `Metadata.GUID`/`Metadata.Type` parse failures; root `GUID` parse failure; empty GUID; missing or unhandled `Type`;
  not an asset type; master bundle override not found; master bundle without an asset bundle; asset bundle version
  out of range.
- A definition without `GUID` (and without `Metadata`): the original writes a new random GUID into the file
  (`Assigned GUID <N> to asset "<path>"`). Pinewatch uses a new random GUID in memory and writes nothing (L3 (e)).
- Internal name, `data` (the `Asset` dictionary if present), master bundle choice (`Master_Bundle_Override`,
  `Exclude_From_Master_Bundle`), bundle relative path (`Bundle_Override_Path`, `Bundle_Path_Include_Filename`),
  hash combination (`Hash.combine(hash, Hash.SHA1(lower-case path))`), effective asset bundle version, legacy ID.

### Task 7: Asset types

**Files:** `crates/pinewatch-assets/src/types.rs`, `crates/pinewatch-assets/tests/types.rs`

Sources: `UnturnedNexus.cs` (the 70 legacy keys), every class deriving from `Asset` (full name, `assetCategory`),
`Bundles/Asset.cs` (`GetTypeFriendlyName`), `Bundles/TypeRegistryDictionary.cs`.

- The legacy registry: an ordinal, case-sensitive map from the 70 keys to types.
- Each type's full name, category and friendly type name (`Consumeable Item`-style splitting at upper-case letters).
- A `TypeResolver` for `Metadata.Type` and v1 `Type` fallbacks: `Type.GetType(name, false, true)` called from
  `UnturnedDat.dll`, so Assembly-CSharp types resolve only when assembly-qualified (V19, partly settled).

### Task 8: Localization

**Files:** `crates/pinewatch-assets/src/local.rs`, `crates/pinewatch-assets/tests/local.rs`

Source: `Files/Local.cs`: `read`, `format`, `FormatOrNull`, `FormatOrEmpty`, `FormatEnglishOrEmpty` and `has`, with

### Task 9: The asset index

**Files:** `crates/pinewatch-assets/src/mapping.rs`, `crates/pinewatch-assets/tests/mapping.rs`

Source: `Bundles/Assets.cs` (`AssetMapping`, `AddToMapping`, `ReportError`), each type's `FriendlyName`.

- The legacy tables per category, the GUID dictionary and list, with `AddToMapping`'s rules: objects without the
  non-zero check, which categories need a legacy ID, overriding origins replacing entries, and the exact messages

- Each type's `FriendlyName`: the bundle name by default; the types that override it read it from their data or
  localization (listed in the task when ported).
